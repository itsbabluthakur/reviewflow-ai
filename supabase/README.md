# supabase/

## Purpose

Everything needed to define, evolve, and secure the Supabase/PostgreSQL database as code, so the schema can be recreated deterministically in any environment.

## Responsibilities

* Track every schema change as a migration.
* Define Row Level Security policies for every tenant-owned table.
* Provide idempotent seed data for local development.
* Host Supabase Edge Functions.

## Structure

```text
supabase/
  migrations/   # Timestamped, ordered SQL migrations (never edited once applied)
  seed/         # Idempotent seed scripts for local/dev environments
  policies/     # Row Level Security (RLS) policy definitions, organized by table/domain
  functions/    # Supabase Edge Functions (Deno runtime)
```

## What belongs here

* SQL migrations generated by the Supabase CLI or Drizzle Kit.
* RLS policy SQL, kept reviewable and separate from table-creation migrations where practical.
* Seed data that is safe to run repeatedly against a fresh database.
* Edge Functions and their local configuration.

## What should NOT be placed here

* Application code, UI, or API route handlers — those belong in `apps/` or `packages/`.
* Secrets or real customer data — seed data must be synthetic.
* Editing an existing, already-applied migration — per [`DATABASE.md`](../DATABASE.md) section 19, schema changes always get a **new** migration.

See [`DATABASE.md`](../DATABASE.md) for the full schema reference and [`SECURITY.md`](../SECURITY.md) sections 5–6 for tenant isolation and RLS requirements.
